# Metro Route

Сервис построения маршрутов в московском метро с двумя интерфейсами:
Telegram-бот и HTTP-сервер.

## Что реализовано

- **Ядро на графе метро.** Реализован алгоритм Дейкстры с двумя режимами оптимизации (по времени и по числу пересадок). При равенстве времени выбирается маршрут с меньшим числом пересадок (и наоборот). Время пересадок учитывается отдельно от времени перегонов.
- **Детализация маршрута.** Путь разбивается на сегменты по линиям, пересадки выделены отдельно.
- **Два интерфейса поверх одного ядра.** Telegram-бот (сценарий с поиском станций и кнопками) и HTTP API (`POST /route`, `GET /stations`, `GET /history/{user_id}`, `GET /healthz`). Ядро не зависит от интерфейса.
- **История запросов в PostgreSQL.** Каждый успешный маршрут сохраняется (пользователь, откуда, куда, режим, время). В боте - команда `/history`, в API - `GET /history/{user_id}`.
- **Тесты.** Юнит-тесты, интеграционные на реальном `metro.json`, тесты всех эндпоинтов API, интеграционные тесты БД (пропускаются без `TEST_DATABASE_URL`).
- **Инфраструктура.** Структурированное логирование (`log/slog`) с уровнями, корректное завершение по сигналу (текущие запросы дорабатывают), ограничение параллелизма через пул токенов, Docker Compose для Postgres + API + бота.
- **Веб-интерфейс.** Фронтенд на HTML/CSS/JS, nginx передаёт статические файлы и проксирует `/api/` в контейнер `api:8080`.

## Быстрый старт

Требования: Go 1.27+, Docker Compose.

```bash
# 1. Создать файл .env и указать
# BOT_TOKEN=...       - токен Telegram-бота от @BotFather
# LOG_LEVEL=...     - вариант вывода логов (info/debug) (по умолчанию info)
# DATABASE_URL=postgres://metro:metro@localhost:5433/metro-db?sslmode=disable - cтрока подключения к Postgres
# TEST_DATABASE_URL=... - строка подключения к тестируемой БД (может совпадать с DATABASE_URL)
# HTTP_ADDR=... - адрес HTTP-сервера (по умолчанию :8080)

# 2. Поднять Postgres
make up

# 3. Запустить HTTP-сервер (Postgres + API)
make run-api
# или Telegram-бота (Postgres + бот)
make run-bot

# 4. Для прекращения работы программы
# Ctrl+C в терминале, где запущен run-api / run-bot - корректное завершение
make down      # остановить контейнеры

# Для более подробной информации о тестировании, сборке, запуске в Docker
make help
```
## Telegram-бот (`cmd/bot`)

**Транспорт:** Telegram Bot API через **long polling**. Бот отправляет `getUpdates` с таймаутом, Telegram держит соединение, пока не появится апдейт (или не истечёт таймаут), и возвращает его. `b.Start(ctx)` запускает цикл long polling; `ctx` отменяет его при Ctrl+C.

**Сценарий диалога**:

1. `/start` → пользователь вводит станцию отправления.
2. Бот ищет станции по префиксу, показывает inline-клавиатуру (до 10 совпадений).
3. Пользователь выбирает станцию (по кнопке) → вводит станцию назначения.
4. Бот снова ищет по префиксу → пользователю представляется клавиатура режимов (`Быстрее` / `Меньше пересадок` / `Свободнее (в разработке)`).
5. Пользователь выбирает режим → бот строит маршрут, сохраняет в историю, отправляет форматированный текст с сегментами и пересадками.
6. Кнопки после маршрута: «Построить новый маршрут» (`/restart`) и «История маршрутов» (`/history`).

**Особенности:**

- **Состояние в памяти**. По ходу диалога сохраняет выбранные пользователем опции в переменную типа `StateStore` (есть синхронизированный доступ). При рестарте бота состояние теряется.
- **`/history` работает в любой момент диалога**. Команда не сбрасывает текущий сценарий. После `/history` можно продолжить построение маршрута с того же места.
- **Пул токенов**. `maxConcurrent = 20`, не более 20 горутин одновременно.
- **`WaitGroup`** для корректного завершения программы. `b.Start(ctx)` возвращается по Ctrl+C, но горутины хендлеров могут ещё работать. `wg.Wait()` с таймаутом 5 секунд ждёт их.

## HTTP API (`cmd/api`)

**Эндпоинты:**

| Метод | Путь | Что делает |
|---|---|---|
| `POST` | `/route` | Принимает выборы пользователя `{from, to, mode}`, возвращает маршрут |
| `GET` | `/stations` | Возвращает список станций (`[]StationView`) |
| `GET` | `/history/{user_id}` | Возвращает последние 10 запросов пользователя |
| `GET` | `/healthz` | Проверяет доступ к БД  |

**Особенности:**

- **`Content-Type: application/json; charset=utf-8`**. Ответы в формате JSON, единый формат ошибок (`{"error": "..."}`).
- **Коды ошибок:**
  - `400` - валидация: невалидный JSON, пустые `from`/`to`, неизвестный `mode`;
  - `404` - станция `from` или `to` не найдена;
  - `422` - нет пути между указанными станциями (скорее теоритическая ситуация);
  - `500` - внутренняя ошибка сервера, включая ошибки БД;
  - `503` - БД недоступна.
- **`POST /route` не возвращает `503` при недоступной БД.** Маршрут строится по графу в памяти. Ошибка сохранения логируется, но код ответа `200`.
- **Пул токенов**. `LimitConcurrency(20)`, не более 20 одновременных хендлеров. Остальные ждут (соединение держится). При завершении (Ctrl + C) `srv.Shutdown` ждёт все активные соединения, включая висящие в пуле, до истечения таймаута (`shutdownCtx`, 5 сек), далее они обрываются.
- **Порядок middleware:** `Logging → Recovery → UserID`. (`UserID` извлекает `X-User-ID`, парсит его в `int64` и кладёт в контекст).

## Ограничения

### 1. Схема метро неполная

В `data/metro.json` только 4 линии (Сокольническая, Замоскворецкая, Кольцевая, Калужско-Рижская).

### 2. Условная авторизация

`X-User-ID` в HTTP API и `chatID` в боте. Клиент может подделать `X-User-ID` и посмотреть чужую историю (`GET /history/{user_id}`). Проверка «`X-User-ID` == `user_id` в пути» защищает только от случайного просмотра. В боте `chatID` приходит от Telegram, его подделать нельзя.

### 3. Нет миграций при создании схемы (в разработке)

Схема создаётся через `SetupSchema` + `data/script.sql` при старте.
